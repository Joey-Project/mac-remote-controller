# Native media remote design and handoff

## Summary

Build a phone remote for sofa media playback while looking directly at the Mac
or connected display. The user selected the first, rectangular-trackpad visual
direction and refined its volume interaction.

## Accepted Scope

- Universal iPhone/iPad app with SwiftUI and UIKit where needed; native Android
  with Kotlin and Jetpack Compose. Swift Mac menu-bar companion. No phone-side
  screen preview. Adapt the Apple mobile layout to iPad sizes and multitasking.
- IINA, Chrome YouTube/Bilibili, and Finder for locating local files.
- The user accepts a companion Chrome extension implemented in TypeScript.
- A selected video source stays pinned independently of foreground desktop focus:
  media buttons can control IINA while the touchpad operates Finder.
- Keep a large rectangular touchpad, fixed playback/seek buttons, and Finder,
  keyboard, and fullscreen shortcuts. Text input submits committed Unicode text.
- Default to system volume. The left volume label is the mode button with a swap
  icon; its tap switches between system and selected-player volume.
- System and player volume values remain independent. Switching mode changes
  neither value. Display the actual value at the right of the heading.
- System volume is continuous. Player volume has invisible 10% steps and a
  stronger, passable detent with haptic feedback at 100%. Show no ordinary ticks.
- Read each player's actual upper bound. IINA can exceed 100%; standard HTML media
  volume is capped at 100%. Never treat 100% as a universal upper bound.
- Unavailable sources and unsupported system-output volume must be explicit,
  without silently targeting another application or volume layer.

## Handoff

- Phase: establish buildable app scaffolds and language checks before product
  implementation at the user's request.
- Keep `apps/macos`, `apps/ios`, `apps/android`, and `apps/chrome-extension`
  separate. iPhone and iPad share the iOS target. Shared Apple code belongs in
  `packages/apple-core`; reserve `packages/protocol` for the agreed wire contract.
- Build/cache ignores belong in each app/package's `.gitignore`; common machine
  and task rules stay at the root.
- Each Apple module owns its Swift format/lint/editor configuration. Shared
  check scripts live in `tooling/swift/`; CI uses Xcode 27.1 with Swift 6.4.
- An initial uncommitted protocol/core sketch and selected image copies are parked
  locally at `.codex-tmp/native-remote-draft/`. They are optional recovery material,
  excluded from this baseline, and must be re-evaluated before use.
- Xcode 26.6 is available. Java 17 is installed; Android SDK, Android Studio, and
  Gradle were absent during the initial environment check.
- Android SDK 37.0, Build Tools 37.0.0, command-line tools 23, and JDK 27 are
  cached locally under `.codex-tmp/android-tools/`. Gradle uses a project-local
  cache there. The ignored Android `local.properties` points to that SDK;
  no global SDK or Java configuration was changed.
- Local Apple validation on 2026-10-17 compiled AppleCore and the macOS app. The
  host's CoreSimulator 1051.54.0 is older than Xcode's required 1051.55.0; both
  generic iOS destinations report the iOS 26.5 platform unavailable. Use the
  required CI Simulator build for validation until the local Xcode components
  are repaired separately. No system component changes were made here.
- Proposed connection design is local discovery plus authenticated, encrypted
  pairing. It remains an implementation proposal, not delivered functionality.

## Next Steps

- Resume from the CI baseline on a separate application branch.
- Define and test the shared command/state contract before splitting native work.
- Implement Mac input/system volume and the native clients against that contract.
- Integrate IINA through its supported plugin API and Chrome through the extension,
  preserving exact target identity and reporting failures.
