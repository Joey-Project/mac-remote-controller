# Parallel Apple CI

## Summary

- Apple builds/package tests, the independent renewal probe, iPhone UI tests and
  iPad UI tests run on separate runners. Both device families run the complete
  existing UI suite, with matrix fail-fast disabled.
- `Swift and Apple apps` remains the required check. Its always-run aggregate
  accepts only successful build, renewal and UI matrix results; failure,
  cancellation, skipped, missing or unknown results cannot pass it.
- Each UI job owns and cleans up only its temporary simulator and uploads a
  device-specific result artifact. Local no-argument execution still tests both
  families sequentially; explicit simulator IDs retain their existing behavior.
- The Xcode/Node/tool versions, test assertions, signing behavior, timeouts,
  audio muting, repository permissions and required-check names are preserved.

## Validation

- Mocked lifecycle scenarios cover each family on success/failure, cleanup,
  default and explicit-ID execution, and argument rejection before side effects.
- Aggregate tests cover every combination of success, failure, cancellation,
  skipped and empty results, plus missing/extra inputs and unknown states.
- Actionlint, shell syntax/ShellCheck, formatting and journal validation check
  the changed workflow and scripts. Actual runner duration is measured by CI.

## Evidence

- Baseline [Apple CI job](https://github.com/Joey-Project/mac-remote-controller/actions/runs/43774438660/job/133035517028):
  80m18s total, including 54m02s for sequential UI tests, 18m41s for Swift checks
  and builds, and 6m39s for the renewal-probe build.
