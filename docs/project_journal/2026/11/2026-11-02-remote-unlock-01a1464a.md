# Paired Phone Remote Unlock

## Scope

Unlock only an already logged-in Mac console session on an explicit request from
an authorized paired iPhone or iPad. Initial login, FileVault preboot and logout
recovery are excluded. Face ID confirmation is deferred. Preserve the existing
remote-control layout and keep unlock work outside the pointer input path.

## Research

Sources were inspected on November 2; upstream behavior is not local acceptance.
The user selected an Authorization Services plug-in; storing or typing a Mac
login password is not part of the chosen backend.

- [BLEUnlock](https://github.com/ts1/BLEUnlock) uses a local Keychain item and
  Accessibility-authorized Unicode keyboard events. Its instructions require
  persistent permission to read that item while the screen is locked. Screen
  locking and Keychain locking must be tested separately. Its source does not
  establish a need for a root helper for this approach.
- [Machine Control's existing-session provider](https://github.com/kzahel/machine-control/blob/main/platforms/macos/guests/macos/unlock/README.md)
  is an MIT reference for a password-free authorization plug-in, authenticated
  root broker and conflict-aware installer. Its source binds expiring one-use
  grants to the console session and boot. The upstream explicitly describes a
  session-wide authorization window and version-sensitive OS integration;
  paired-phone authorization still needs our own design and validation.
- [NoMAD Login AD](https://github.com/jamf/NoMADLogin-AD) is MIT licensed but
  archived. [XCreds](https://github.com/twocanoes/xcreds) is BSD licensed and
  integrates cloud authentication with the Mac login process. These are broader
  architecture references rather than drop-in phone-unlock components.

Only bounded public-source reference snapshots were saved under the ignored
task cache. No upstream installer or downloaded executable was run.

## Native Canary

- Add an original Objective-C callback bundle and bounded, one-use grant storage
  in `apps/macos/UnlockCanary`. Continuous time includes sleep. Grants require
  the same user, console-session UUID and boot UUID, and refuse locked sessions.
- The canary exports no real-unlock mechanism. Its explicit administrator
  installer owns only a separate test right, checks a reviewed artifact
  fingerprint, refuses replacement conflicts and preserves interrupted intent.
  The system screen-lock definition is compared before/after, never rewritten.
- Add native callback/filesystem/concurrency checks and offline installer
  admission checks. CI builds/tests this stage without privileged installation.
- Serialize cooperating publication, consumption and cancellation with a
  nonblocking directory lock acquired before any grant is opened. A replacement
  cannot publish between an old claim and its cleanup. The native callback
  samples OS state/time at the decision and accepts only the two exact canary
  mechanism-name representations.
- A read-only probe observes this Mac as locked outside the sandbox; inside the
  sandbox it returns unknown. Those are distinct observations.
- The first administrator-approved physical installation exposed macOS rule
  normalization: the system adds its `security` creator requirement and omits
  a mechanism timeout. Match that exact supported representation and reject
  foreign creators or behavioral fields. Add fingerprint- and signature-bound
  removal for the narrowly identified published-but-incomplete state; unknown
  staging or changed artifacts remain manual diagnosis.
- Installation and teardown share the native grant-operation directory lock.
  Check the complete fixed bundle tree before any publication or removal so
  extra entries cause an early refusal and preserve the existing components.
- Native compilation and local ad-hoc signature verification are separate from
  authorization-host loading and actual screen-unlock acceptance. At the initial
  source-validation checkpoint, no password was collected and no helper,
  authorization right or login policy was installed.

See [the native canary guide](../../../../../apps/macos/UnlockCanary/README.md).

## Native Canary Acceptance

The administrator-approved canary installation demonstrated actual plug-in
loading: absent grants denied, a fresh grant allowed, replay denied, and expired
grants denied. Cleanup removed the dedicated right and all three fixed paths;
the existing screen-lock rule was unchanged. This proves the inert canary only.

## Runtime and Menu Integration

- Add a launchd/XPC broker, signed root-private installer and a separate runtime
  plug-in. Installation starts disabled; enablement preserves existing fallback
  branches, and disable/uninstall restore only a matching owned policy.
- Bind the broker to the current companion hash/UID and each request to an
  allowed paired device. One-use grants require a live broker generation and
  expire after five seconds; no work runs in the pointer input path.
- Add helper installation, update, enable/disable and removal to the existing
  Mac menu-bar setup area. Add a capability-gated iOS unlock menu action without
  changing the touchpad or media layouts.
- Add manual phone recovery in the same setup area, using a private accepted
  app copy and existing probe session. USB and unlocked devices are permitted
  only in explicit manual mode; daily research defaults remain unchanged.
- The native trigger uses the exact secure field's Accessibility confirmation,
  without reading its value or sending keyboard events. Where character-count
  metadata is unsupported, a successful native empty write precedes confirmation;
  known nonempty fields, failed writes and other read errors are refused.
  OS unlock observation is required independently; failed preparation cancels
  the grant. Installation/enablement explicitly request missing Accessibility.
- Retain device denials until authenticated helper status confirms removal.
  Reconcile helper permissions against the loaded paired-device list to recover
  orphaned denials after companion restart; retry after status refresh rather
  than spinning on an unavailable helper.

See [the runtime and recovery guide](../../../../../apps/macos/UnlockRuntime/README.md).

## Source Validation

- Local Xcode 26.6 / Swift 6.3.3: 239 shared-package tests, Swift format and
  SwiftLint, signed universal macOS builds including incremental signing, and
  generic iOS Simulator compilation. CI separately selects Xcode 27.1.
- The packaged companion has Hardened Runtime enabled, no debug/injection
  entitlements, and passes strict deep signature validation. Native runtime
  grants pass 77 checks; the canary installer and renewal tooling each pass
  28 offline tests.
- iOS 26.5 Simulator: iPhone 17 Pro has 11 passing cases and two explicit skips;
  iPad mini has 12 passing cases and one live-media skip. All three new unlock
  menu cases run and pass on both. Preserve the initial iPad rotation failure
  and incomplete iPhone test-group run separately from the final full cases.
  The landscape test waits for stable window/surface geometry while retaining
  all original boundary assertions and product layout.
- Signature inspection of the immutable running process is cached. Fresh
  staged-copy verification and XPC peer checks remain mandatory. Lock-result
  polling runs only during an active request, independently of pointer input.
- Real signature probes caught a bootstrap CLI error before installation.
  Verify the entire staged bundle recursively, then separately check the pinned
  main identity for the running architecture with an inline `=` requirement.
  Three real-signature regression tests cover universal code, distinct nested
  identities, re-signed replacement, wrong main hash, and parent-link escape;
  metadata-only timestamp changes remain valid. Privileged nested images use
  ad-hoc signatures so their designated requirements pin their exact slices.
- Installation accepts the root-owned shared helper directory with either
  `0755` or `1755`, preserving its existing sticky bit. Group/other write access,
  other special bits, wrong ownership and links remain refused; private state
  directories retain exact-mode checks. The host's `1755` directory exposed the
  earlier overly strict preflight before any runtime files or lock-rule changes.
  Regression checks preserve directory identity, ownership and mode across
  admission and reject actual access-policy changes.
- Keep installation failure text visible through periodic status refreshes until
  the next explicit setup/settings operation, so a failed install is diagnosable.
- Physical read-only inspection found the secure password control and advertised
  `AXConfirm`, while `AXNumberOfCharacters` returned unsupported (`-25205`).
  The temporary diagnostics grant and app were removed after capture. Regression
  checks cover empty-write ordering, control identity, failure, cancellation and
  context changes without password-value reads or keyboard input. Uncertain
  confirmation replies require independent OS observation and are never replayed.
- Local development copies can confuse Launch Services and leave an allowed
  Accessibility entry bound to an old code hash. Keep only the fixed companion
  registered and retain rollback bundles outside Applications. A same-build
  permission identity check distinguishes this from actual native activation.

## Next Validation

- Review the complete runtime before privileged installation or enablement.
- Verify missing, expired, replayed and wrong-session grants are refused;
  disconnect, revoke, sleep or user switching must invalidate authority.
- Independently observe actual OS unlock. A callback success or successful
  authorization-right evaluation alone is insufficient.
- Verify ordinary password/Touch ID fallback, bounded failure, Keychain health,
  disable/uninstall rollback and coexistence with existing authorization plug-ins.
- Treat physical-host compatibility and the phone-to-helper path as separate
  acceptance gates. Resolve the native trigger separately: upstream Return-key
  activation is not evidence of a keyboard-free system unlock path.
