# Paired Phone Remote Unlock

## Scope

Unlock only an already logged-in Mac console session on an explicit request from
an authorized paired iPhone or iPad. Initial login, FileVault preboot and logout
recovery are excluded. Face ID confirmation is deferred. Preserve the existing
remote-control layout and keep unlock work outside the pointer input path.

## Research

Sources were inspected on November 2; upstream behavior is not local acceptance.
The user selected an Authorization Services plug-in; storing or typing a Mac
login password is not part of the chosen backend.

- [BLEUnlock](https://github.com/ts1/BLEUnlock) uses a local Keychain item and
  Accessibility-authorized Unicode keyboard events. Its instructions require
  persistent permission to read that item while the screen is locked. Screen
  locking and Keychain locking must be tested separately. Its source does not
  establish a need for a root helper for this approach.
- [Machine Control's existing-session provider](https://github.com/kzahel/machine-control/blob/main/platforms/macos/guests/macos/unlock/README.md)
  is an MIT reference for a password-free authorization plug-in, authenticated
  root broker and conflict-aware installer. Its source binds expiring one-use
  grants to the console session and boot. The upstream explicitly describes a
  session-wide authorization window and version-sensitive OS integration;
  paired-phone authorization still needs our own design and validation.
- [NoMAD Login AD](https://github.com/jamf/NoMADLogin-AD) is MIT licensed but
  archived. [XCreds](https://github.com/twocanoes/xcreds) is BSD licensed and
  integrates cloud authentication with the Mac login process. These are broader
  architecture references rather than drop-in phone-unlock components.

Only bounded public-source reference snapshots were saved under the ignored
task cache. No upstream installer or downloaded executable was run.

## Native Canary

- Add an original Objective-C callback bundle and bounded, one-use grant storage
  in `apps/macos/UnlockCanary`. Continuous time includes sleep. Grants require
  the same user, console-session UUID and boot UUID, and refuse locked sessions.
- The canary exports no real-unlock mechanism. Its explicit administrator
  installer owns only a separate test right, checks a reviewed artifact
  fingerprint, refuses replacement conflicts and preserves interrupted intent.
  The system screen-lock definition is compared before/after, never rewritten.
- Add native callback/filesystem/concurrency checks and offline installer
  admission checks. CI builds/tests this stage without privileged installation.
- Serialize cooperating publication, consumption and cancellation with a
  nonblocking directory lock acquired before any grant is opened. A replacement
  cannot publish between an old claim and its cleanup. The native callback
  samples OS state/time at the decision and accepts only the two exact canary
  mechanism-name representations.
- A read-only probe observes this Mac as locked outside the sandbox; inside the
  sandbox it returns unknown. Those are distinct observations.
- The first administrator-approved physical installation exposed macOS rule
  normalization: the system adds its `security` creator requirement and omits
  a mechanism timeout. Match that exact supported representation and reject
  foreign creators or behavioral fields. Add fingerprint- and signature-bound
  removal for the narrowly identified published-but-incomplete state; unknown
  staging or changed artifacts remain manual diagnosis.
- Installation and teardown share the native grant-operation directory lock.
  Check the complete fixed bundle tree before any publication or removal so
  extra entries cause an early refusal and preserve the existing components.
- Native compilation and local ad-hoc signature verification are separate from
  authorization-host loading and actual screen-unlock acceptance. At the initial
  source-validation checkpoint, no password was collected and no helper,
  authorization right or login policy was installed.

See [the native canary guide](../../../../../apps/macos/UnlockCanary/README.md).

## Next Validation

- Investigate the password-free plug-in in an isolated test environment before
  selecting a production backend or changing this Mac's authentication chain.
- Pin and inspect any adopted upstream source and preserve its license.
- Verify missing, expired, replayed and wrong-session grants are refused;
  disconnect, revoke, sleep or user switching must invalidate authority.
- Independently observe actual OS unlock. A callback success or successful
  authorization-right evaluation alone is insufficient.
- Verify ordinary password/Touch ID fallback, bounded failure, Keychain health,
  disable/uninstall rollback and coexistence with existing authorization plug-ins.
- Treat physical-host compatibility and the phone-to-helper path as separate
  acceptance gates. Resolve the native trigger separately: upstream Return-key
  activation is not evidence of a keyboard-free system unlock path.
